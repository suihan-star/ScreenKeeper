# 019 · macOS Apple Silicon 版设计

关联 [开发计划](019-macos-apple-silicon-plan.md)。记录日期：2026-11-10。用户已确认实施，随后明确暂时没有 Mac，先完成源码、由朋友帮助测试。本轮建立独立原生开发预览；Mac 编译和硬件兼容结果仍待验证。

## 已确认需求

- 用户反馈当前 Windows 版运行没有问题，希望以当前产品为基础开发 Mac 版，只支持 Apple Silicon（M 系列），不开发 Intel 版。
- 目标覆盖 M 系列 Mac，不用具体芯片代际或显示器品牌白名单限制应用安装。首版代码采用 macOS 13 部署目标（SwiftUI 布局与原生 API 基线），不等于已经验收该系统及全部后续版本。
- 单屏与多屏都可使用。外接屏数量、型号和连接方式由用户决定，应用动态识别系统提供的屏幕，不写死双屏，也不要求用户预先提供型号才能配置。
- 实机型号用于安排测试，不能据此把产品设计为仅适配测试者的设备。Windows 验收不构成 Mac 验收，也不自动把测试 ZIP 更名为正式包。

## 产品行为与兼容边界

“都能适应”落实为动态布局、逐屏配置、能力检测和局部降级，而非承诺所有硬件支持相同的底层操作。

| 范围 | 设计目标 | 不可用时的行为 |
| --- | --- | --- |
| 屏幕发现 | 内置屏、外接屏动态增减；适配分辨率、缩放、旋转及主屏变化 | 未识别稳定身份时提示重新关联，不能把旧屏配置套给另一块屏 |
| 屏幕休息 | 先支持软件遮黑；保留每屏计时、唤醒条件、暂缓和跨屏应用设置 | 软件遮黑不宣传为硬件断电或节能；硬件休眠、亮度另行验证 |
| 隐私幕 | 保留默认山林、自定义图片、明确进入按钮和使用时免打扰 | 覆盖失败必须报告，不能宣称已保护；原生全屏和 Spaces 必须实测 |
| 回到桌面／指定应用 | 按目标屏幕操作窗口；按需请求辅助功能权限 | 未授权、不支持窗口控制、跨屏归属不清时保留已建立的幕布并说明原因 |
| 健康提醒 | 独立全局周期、提醒与休息画面、暂停和跳过；自动适应目标屏尺寸 | 宿主断开或会话锁定时停止展示，不跳到其他屏泄露内容或打断工作 |
| 色温 | 保留逐屏作息、原色／自定义、试调和恢复保护的产品规则 | 按屏检测和实机验证；不可用不阻断其他屏幕或其他模块 |
| 硬件亮度 | 作为独立可选能力研究 | 不支持时明确显示不可用；软件变暗必须使用不同名称 |

软件不额外设置固定屏幕数量上限，但只能管理 macOS 实际提供的显示区域。Mac 自身可连接的屏幕数量还受机型、分辨率与刷新率影响；应用不能突破该硬件边界。镜像屏共享画面，不能作为相互独立的隐私画面处理。虚拟屏、DisplayLink、Sidecar 和远程会话需独立检测，不因被枚举出来就认定可写 Gamma 或硬件亮度。

按屏呈现“可用／需要授权／等待连接恢复／此连接不支持／需要检查”等具体状态。瞬时断开不删除配置；同型号加编号只用于显示，不作为持久化身份。保存和放弃仍以模块为单位，插拔不得覆盖未保存草稿。

## 实现路线

使用 SwiftUI 构建设置界面，AppKit 管理菜单栏、窗口和覆盖层，Core Graphics／Accessibility 承担相应系统适配。Swift tools version 5.9、最低 macOS 13；采用 Swift Package 的 Core 库与 Mac executable 两目标，非 Mac 主机仅加入核心与测试。产品构建脚本要求原生 arm64 Mac，生成本地开发 `.app` 和 ZIP；使用 Xcode 15+ 或兼容的 Command Line Tools。

原 `OLED-Sleeper/OLED-Sleeper.csproj` 是 `net8.0-windows` WPF 项目。WPF 仅运行于 Windows，不能通过修改发布架构得到 Mac 应用；本次 Mac 客户端独立实现。

- 可沿用：功能分区、交互规则、中英文文案、静绿／雾白绿主题语义、SVG 图标与山林背景、计时和日程规则、回归场景。
- 需要迁移而非直接编译复用：C# 日程与状态机。采用 Swift 路线时，通过同一组输入／预期输出样例验证两端规则一致，不为此立即重构稳定 Windows 版。
- 需要重写：WPF 界面、托盘、原生输入／会话接口、窗口操作、显示器身份、Gamma 和硬件亮度后端、启动项及打包。
- 现有色温接口不等于完整跨平台隔离：恢复服务仍引用 `WindowsGammaBackend.SameScope`，数据表示与 Windows Gamma 绑定。Mac 必须定义自己的颜色数据、设备身份和作用域规则。

本仓库独立 `macos/` 目录开发，保留现有 Windows 解决方案、构建和发布入口。素材复用保留来源及许可；Mac 菜单栏采用模板图像，应用图标由 Mac 原生导出脚本生成，实际清晰度与外观待 Mac 验收。

## 显示控制与恢复

1. 能力探测与实际接管分开。读取接口成功、写入返回成功均不能证明用户看到正确、独立且可恢复的效果。
2. 色温先完成原色读取、耐久恢复日志、指定屏幕受控试调、独立性和恢复确认，再开放保存策略。不给未知屏幕套用另一屏的验证记录。
3. Night Shift、True Tone、HDR／EDR、ColorSync 配置和其他调色工具纳入兼容研究；不自动关闭用户系统设置，也不接纳未知颜色为新原色。
4. 优先验证关屏过夜、锁屏、睡眠、合盖、扩展坞插拔后的恢复。借鉴 Windows 的稳定采样与所有权保护原则，但具体判定必须建立在 Mac 实测之上。
5. 权限按功能请求，拒绝或撤回时仅限制依赖功能。不记录按键、窗口内容或截图；窗口选择器确需的标题仅临时展示，不进入日志与配置。未证明必需前不索取屏幕录制权限。
6. 普通第三方窗口覆盖不等于系统锁屏，不承诺覆盖登录、安全界面或所有系统级画面。Spaces、原生全屏及台前调度是首轮验证项，不能只靠窗口层级推断保护有效。

## 数据、构建与回退

- Mac 数据位于 `~/Library/Application Support/ScreenKeeper`，配置为 `mac-settings.json`，schema 1；进程锁为 `mac-instance.lock`。不导入 Windows 的设备身份、原色、恢复或验证文件，不读取 OLED Sleeper 数据。
- 先固定 macOS 配置 schema 和备份／原子写入策略，再接入设备写入。业务选项可设计未来显式导入，恢复日志不可跨系统迁移。
- 仅生成 arm64 应用。当前脚本已实现开发 `.app`／ZIP／DMG 和 ad-hoc 签名流程，但尚未在 Mac 实际执行；不是 Developer ID 或公证。正式分发的签名、公证和安装验收仍待后续执行。
- 不改已交付 Windows 包与正在运行的配置；Mac 调色停止后须确认恢复，才能切回旧构建。未知恢复状态不得通过删除日志消除。

## 资料与当前证据

- [WPF 官方说明：仅运行于 Windows](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)。对应本仓库 `OLED-Sleeper/OLED-Sleeper.csproj`。
- [Apple MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra)：原生菜单栏界面路线的参考。
- [Apple Quartz Display Services](https://developer.apple.com/documentation/coregraphics/quartz-display-services)：包含显示枚举与 Gamma 接口；接口存在不是 M 系列各连接方式的兼容证明。
- [Apple Accessibility 接口](https://developer.apple.com/documentation/applicationservices/axuielement_h)：窗口控制能力研究入口；目标应用可能未实现某些操作。
- [Apple 外接屏支持说明](https://support.apple.com/en-us/122212)：以 MacBook Air 为例说明机型、分辨率和刷新率共同影响连接数量，不据此限定本产品支持机型。

以上于 2026-11-10 查询。尚未在 Mac 上编译、运行或写入显示设备；最终功能开放范围由能力验证结果决定。

## 首次源码交付的明确范围

已实现基础设置、模块保存／放弃、复制设置、单实例锁、动态屏幕列表、软件休息、隐私幕及图片、健康周期与居中操作卡、只读诊断和构建入口。色温只有纯日程逻辑与只读探测，未加入 Gamma 写入后端；硬件亮度、断电、桌面／指定应用、开机启动、全屏免打扰和动态雾光均未开放。不能把这些源码状态描述为 Windows 完整功能已移植。

会话适配只使用公开通知及 console/login 元数据，不读取私有锁屏字段。启动和睡眠后等待交互确认可能使自动计时延后到打开设置；已有隐私幕在此期间保留，普通输入不解除。不同系统的锁屏通知覆盖须实测。设置窗口关闭／最小化仅撤销预览，退出前的未保存确认位于自有幕布之上；确认退出才清理全部窗口。

## 云端构建与测试者交付

**最新决定：** 用户随后明确要求将完整项目托管到新建 GitHub 仓库，执行方案以 [020 托管设计](020-github-hosting-design.md) 为准。此前最小私有副本方案不再采用，历史源码快照仅留存；手动 workflow 直接构建完整仓库的精确提交。以下保留前期方案和决策依据，不代表已执行上传。

用户认为源码构建步骤过重，要求继续处理为朋友可直接运行的包。开发者负责构建，测试者不安装 Xcode。现有环境没有可用 Mac；拟用 GitHub Actions 标准 `macos-15` arm64 runner，执行测试、发布构建、二进制／资源检查和打包。Codeup 仍是产品主仓库，不改 origin 或上传整个脏工作区。

用户随后确认源码放在现有项目或 Codeup；采用现有仓库的 `macos/`，不另拆主仓库。云效官方托管构建集群为 Linux，macOS 节点需要自行提供，换建 Codeup 仓库不能解决编译机器缺失。借用 GitHub 构建服务及私有源码副本仍是待授权选项，不把源码存放位置的选择当作已授权新服务。

新增手动 workflow，不在 push／PR 自动运行，不创建 Release；一次 job 最多 20 分钟、产物保留 3 天。云端用受控最小源码快照，只包含 Mac 源码、资源、许可及该 workflow，排除用户配置、Windows 工作区和已有产物。首次上传前明确 GitHub 账号、私有仓库和费用边界；没有授权连接时仅准备本地文件，不宣称构建已开始。

构建前固定并校验 SHA256 清单，记录实际 Swift／Xcode／SDK、源码提交和清单哈希。无界面环境不调用 Finder。产物提供 ZIP 与拖入 Applications 的 DMG，附中英说明、签名状态和校验值；启动自检只核对资源／身份，不启动业务或接管显示器。

默认仍为 ad-hoc 开发签名，首次打开可能需要 macOS 对单个可信应用的确认，不关闭 Gatekeeper。要达到正常识别开发者的外部分发体验，需用户提供已持有的 Developer ID 身份，并另行配置 hardened runtime、公证与 staple；不自动购买账户或创建证书。GitHub 私有仓库消耗账户包含额度，不能未经核对承诺永久免费，也不自动开启付费。
