## 范围与证据顺序

1. 确认运行路径、构建身份及文件完整性，区分安装版与便携版数据。
2. 交叉核对 Windows 应用错误、WER、应用日志与现有崩溃转储；仅提取异常类型、线程调用栈和模块等诊断信息，不上传转储或读取窗口内容。
3. 只读核对色温保存策略、恢复记录、当前显示作用域和 Gamma，并检查调色进程。进程存在只能作为候选原因，不等同于确认它执行了某次写入。
4. 分别报告已确认事实、假设、未验证项。只有故障证据能支持具体根因时才设计代码修复，不通过放宽颜色所有权检查或删除记录掩盖问题。

## 验证与边界

本轮不自动切换色温、不关闭其他软件、不更改用户配置、恢复记录或系统调试配置；只读查询和本地转储分析不构成硬件恢复验收。调色对照需要用户先停用其他调色来源并方便观察。修复如涉及生产代码，补充本计划的实现与回归步骤后执行。

## 已确认缺陷与最小修复

15:27 与 18:01 转储均包含重复的 `UpdateCapabilities → EndPreviewAsync → CancelPreviewAsync → ColorChanged → UpdateCapabilities` 托管调用链。`SelectedScreen` 在调用 `LeavePage` 之后才更新字段；取消预览的同步状态通知仍看到已经失效的旧选屏，再次触发同一 setter。根因是状态发布顺序，不是应该删除冲突保护。

修复时在任何取消操作／通知前同步提交选屏与预览目标，保持取消旧试调、保留草稿和按新目标展示的行为。回归覆盖选屏因冲突被移除、有替代屏／无替代屏、同步取消回调的重入、手动切屏与直接切换试调目标。使用受控回调次数上限安全复现，不让旧代码把测试进程压垮。之后运行色温相关和完整测试、构建与格式检查；不自动覆盖用户正在使用的便携目录。09:48 的访问冲突独立分析，未经证实不合并归因。

## 2026-10-09 · 新系统 SDR 识别修复

用户在测试包中报告两屏均提示 HDR／高级颜色不满足 SDR。只读复核确认 Windows 11 build 26300 下，DELL SE2723DS 与 Q27P10 的旧接口均返回 flags=5（advancedColorEnabled=false、wideColorEnforced=true），新接口均成功返回 flags=69、activeColorMode=SDR、advancedColorActive=false；两屏都是扩展模式。旧实现将 flags 的 bit1／bit2 一并视为正在使用高级颜色，在该环境误拒绝普通 SDR。这不构成显示器硬件故障证据。

使用微软 SDK 定义的 `DISPLAYCONFIG_GET_ADVANCED_COLOR_INFO_2`（只读请求 15）优先确认实际模式。只有明确 SDR 且非 active 时才允许后续资格检查；HDR、WCG、未知模式、查询异常及前后查询状态冲突继续阻止接管。旧系统不支持新请求时回退原有保守判断，不把“支持高级颜色”误当作“已启用”。原接口字段继续参与作用域指纹；确认 SDR（含旧系统保守回退确认的 SDR）保持既有指纹，非 SDR 或不确定状态增加模式后缀，使只读恢复复核同样拒绝过期作用域。不放宽验证、精确作用域和恢复所有权检查。

实现范围限定于原生只读查询、后端资格计算及其单测；补充本机只读对照，不自动写 Gamma 或修改 Windows 设置。修复后提供独立编号的 x64 测试 ZIP，保留前一测试包和稳定包；正式双架构包继续等待用户实测。回滚为保留的上一测试包，不能通过删除恢复日志回滚。

定义依据：[Microsoft win32metadata / wingdi.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/wingdi.h)。高级颜色包括 SDR 的自动颜色管理场景，不能与 HDR 等同：[Microsoft Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)。
