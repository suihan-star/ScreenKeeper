# 屏幕良伴 · ScreenKeeper 64 位测试版

版本：1.0.1-alpha.0.1；构建：20261009.3。适用 Windows 10／11 x64。

这是自动退出与 SDR 识别问题的修复测试包，等待实机观察，不是新的正式稳定版。

## 本次修复

新增修复：部分新版 Windows 会在实际为 SDR 时返回旧广色域标志，之前会误报 HDR／高级颜色不满足条件。现在优先查询系统的实际 SDR／WCG／HDR 模式，真正的高级颜色、未知状态及恢复保护仍然拦截。只读核对本机 DELL SE2723DS 与 Q27P10 均已不再被此误判阻塞；这不等于自动通过实机验证。无需为这次误判反复开关 HDR。

从 20261009.1 测试包更新时，仍按下方步骤退出后复制完整 Data，并从新目录启动。若连接或模式已变，仍可能需要按程序提示完成原色处理和逐屏验证；本包不自动清除记录。

色温状态变化导致当前屏幕不可用时，选屏与取消试调可能反复触发界面刷新，最终造成栈溢出退出。本次改为先同步更新所选屏幕与试调目标，再取消旧试调，保留各屏幕草稿和原色恢复保护。

本次没有绕过色温验证或外部改色保护。其他调色来源仍可能覆盖色温；10 月 8 日早上另一次异常的原始业务栈不完整，因此不能保证已经消除所有退出原因。

## 在当前电脑测试

1. 从旧版托盘菜单完全退出，等待退出与恢复提示处理完；关闭主窗口只会隐藏到托盘。
2. 将 ZIP 完整解压到一个新文件夹，保留旧版整个目录。不要只复制 EXE，也不要在压缩软件中运行。
3. 如需沿用当前电脑的设置，在两份程序均已退出时，把旧程序旁的**完整 Data 文件夹复制**到新程序的 ScreenKeeper.exe 旁。复制后应为 `ScreenKeeper/Data/ScreenKeeper/`。保留全部恢复记录、验证记录和图片，不只挑选 settings.json。不要把其他电脑的 Data 复制过来。
4. 双击新文件夹中的 ScreenKeeper.exe。使用旧快捷方式会启动旧版；请从新文件夹启动，并通过 VERSION.txt 或 EXE 的属性核对预发布版本。
5. 测试色温前完整退出 f.lux 等其他调色软件，并关闭 Windows 夜间模式；不同时运行两份屏幕良伴。

如果仍显示「查看处理步骤」，先关闭并保存色温策略，再按软件中的「重新检查原色」处理。当前颜色仍不匹配时，不反复删除记录或强行验证；仅在确认当前画面正常后按「重新建立原色」和观察验证流程处理。该流程不会自动开启调色，验证通过后需自行开启所选屏幕并保存。

## 重点观察

- 日常使用、切换所选屏幕、切换页面、结束试调及发生恢复提示时，软件是否仍会自动退出。
- 色温保存后是否持续生效；正常经过工作／休息时段及锁屏恢复后，是否又出现处理提示。记下大致时间、屏幕型号，以及当时是否刚开关显示器或恢复锁屏。
- 可以先使用半天到一天；若再次退出或失效，保留 `Data/ScreenKeeper/Logs` 和现有恢复记录，不用重复重新建立原色来掩盖现场。

切回旧版前，在测试版关闭色温／屏幕休息并保存、确认颜色与亮度已恢复，再从托盘退出。如恢复仍有冲突，先处理提示，不用旧 Data 覆盖新的恢复记录。程序未签名；本包等待用户实测，不代表所有硬件问题都已验收。

完整通用帮助见同目录的「使用说明-README.txt」和「常见问题-FAQ.txt」。

# ScreenKeeper x64 test build

Version: 1.0.1-alpha.0.1. Build: 20261009.3. Windows 10/11 x64.

This prerelease tests unexpected-exit and SDR detection fixes; it is not a new stable release.

## What changed

New fix: some recent Windows builds return a legacy wide-color flag while the display is actually in SDR. The previous check incorrectly blocked such displays. The backend now reads the actual SDR/WCG/HDR mode first. Active advanced color, unknown states and recovery safeguards remain blocked. Read-only checks on the local DELL SE2723DS and Q27P10 now pass the SDR gate; this does not grant observed validation automatically. Repeatedly toggling HDR is not a solution for this detection bug.

When updating from build 20261009.1, exit first and copy the complete Data folder as described below. Connection or mode changes may still require the existing baseline recovery and per-display observation flow. Records are not automatically cleared.

When a color display became unavailable, selection changes and preview cancellation could recursively refresh each other until the application crashed with a stack overflow. Selection and preview targets now update before canceling the old preview. Draft settings and color recovery safeguards remain intact.

Other color tools or display events can still override the current color. One earlier crash had an incomplete original application stack, so this build does not claim to fix every possible exit cause.

## Test on the same PC

1. Exit the old copy from its tray menu and finish any recovery prompts. Closing the settings window only hides it.
2. Extract the entire ZIP into a new folder and retain the complete old folder. Keep every DLL beside the EXE; do not run from inside the ZIP.
3. To keep your settings on this PC, with both copies closed, COPY the entire old Data folder beside the new ScreenKeeper.exe. The result is `ScreenKeeper/Data/ScreenKeeper/`. Keep all recovery, validation and image files. Do not copy only settings.json or reuse another PC's Data.
4. Launch ScreenKeeper.exe from the new folder, not an old shortcut. Check VERSION.txt or the EXE's file properties for this prerelease version.
5. Before testing color temperature, fully exit f.lux and other color tools and turn off Windows Night Light. Run only one ScreenKeeper copy at a time.

If recovery steps are shown, turn off and save the color policies, then follow the app's original-color recheck. If the color still differs, use the baseline re-establishment and observation-validation flow only after confirming that the current image looks normal. Do not delete recovery records or repeatedly bypass the prompt. Validation does not enable color adjustment automatically; enable the intended display and save afterwards.

Observe normal use, display/page switches, preview cancellation, schedule boundaries and lock/unlock. If an exit or lost color occurs, note the approximate time, display model and any preceding display-power or session changes. Keep Data/ScreenKeeper/Logs and all recovery records. Half a day to a day is a useful initial observation period, not proof of universal compatibility.

Before returning to the old copy, disable and save color and screen-rest controls in the test build, confirm color/brightness restoration, and exit via the tray. Resolve pending recovery first; do not overwrite newer recovery records with old Data. This build is unsigned and still requires real-device observation.

The bundled README and FAQ contain the full bilingual usage instructions.
